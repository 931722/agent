# 作業二系統說明

本階段將第一次規劃轉成單店可執行雛形。核心流程是：使用者輸入 → Agent 選擇工具 → 工具執行 → Agent 讀取結果 → 最後回覆。使用本機 Ollama 原生工具呼叫，不要求所有工作都由模型計算。

## 為什麼保留演算法

Agent 負責理解需求、決定需要查詢或計算什麼；FIFO 工具負責嚴格的工序依賴與設備、人力配對。把演算法包裝成工具可以重現和測試結果，避免模型直接猜測誰該做哪一道菜。

本專案是單一 Agent 的受控 Tool Use 流程。模型可以根據工具結果提出下一次工具呼叫，但程式限制工具清單、參數及次數。不宣稱已實作完整 ReAct，也沒有使用多 Agent、自我反思或 RAG。配方、技能、站點是結構化資料，暫不需要文件檢索。

## 與第一次規劃的差異

| 第一次規劃 | 作業二實際範圍 | 理由與後續 |
| --- | --- | --- |
| PostgreSQL | SQLite 單店狀態快照與交易 | 降低雛形部署成本；使用寫入交易保護確認與雙資源保留 |
| 詳細料理 DAG | 每份菜烹調 → 出餐 | 先驗證先後依賴與不同工作站；備料、清潔及批次後續擴充 |
| FIFO、Hybrid 等比較 | FIFO 基線 | 保留清楚的基準，混合加權策略後續獨立評估 |
| 資源受限 ETA | 最早完成下界與風險提醒 | 尚未做完整未來排程推演，不把下界宣稱為 ETA |
| 對話記憶 | 單次工具循環，跨次不保留聊天上下文 | 營運狀態與紀錄有持久化；多輪語意記憶留作後續 |
| 事件自動重算 | 事件更新狀態，下一次使用者請求重算 | 先展示明確可控制的輸入和回饋循環 |
| 即時餐廳／POS | 虛構資料與手動模擬時間 | 沒有實際餐廳資料或試點效益聲明 |

## 設計重點

- 三個可呼叫工具：查詢狀態、建立排程、查詢風險。
- 指派前須同時滿足工作站類型、廚師技能及資源空閒條件。
- 模型不能直接確認、開工、完成或修改設備；這些操作由介面控制。
- 提案版本與目前狀態不符時拒絕，防止舊畫面指派過時資源。
- 執行中工序不重排，完成必須由人工回報。
- 每次 Agent 執行有可下載的 JSON 紀錄，明示模型模式及失敗原因。

## 三分鐘展示順序

1. 說明使用者、問題、資料是假設情境。
2. 展示 Ollama 模式與使用模型，再輸入「請安排下一批工作」。
3. 展開查詢及排程工具呼叫，說明輸入、輸出和 FIFO 限制。
4. 確認派工、開工、推進時間與回報完成，展示依賴解鎖。
5. 示範舊提案被拒絕，或停用所有烹調工作站後無法排程。
6. 展示 Podman 執行環境及 README，下載真實執行紀錄。

## 後續改善方向

作業三可固定模型和 FIFO，加入更完整的工具結果驗證、有限次重試與對話狀態，再比較至少 10 個案例的成功率、錯誤回覆及工具呼叫成本。排程策略也能另做 Hybrid 比較，但要與 Agent 改善分開歸因。
